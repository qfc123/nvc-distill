# 把一本书蒸馏成一个 Skill · 六步法

本文档记录 `nvc-distill` 的实际生产过程，供复用。**本仓库原创方法**，与《非暴力沟通》内容无关。

---

## 0 · 先判断：这本书适不适合做成 Skill

适合蒸馏的书有三类特征：

1. **有可执行的框架**，而不只是观点（能回答"遇到 X 情况该怎么做"）。
2. **有可枚举的清单**（词表、步骤、反模式、判据），这类内容最容易被 AI 稳定复现。
3. **术语体系稳定**，不然后续一致性维护成本极高。

不适合的：纯叙事作品、观点随章节漂移的随笔。

---

## 1 · 章节切分：拿到可定位的坐标系

- 用 Python `zipfile` **只读打开** epub（不解压落盘），按 `OEBPS/Text/chapterN.xhtml` 抽出带编号的段落。
- 先建立 **章节 → 文件 → 段号** 的映射表，后续每个知识点都能定位到具体段落。
- 顺手把每章的小节标题抽出来，它就是这本书的骨架。

> 这一步的产物是 `docs/SOURCES.md` 的左半张表。没有坐标系，后面所有溯源都是假的。

## 2 · 知识点抽取：先找"判据"，再找"道理"

抽取时按优先级排序：

| 优先级 | 抽什么 | 为什么 |
|---|---|---|
| 最高 | **清单**（词表、步骤、分类、反模式） | AI 最容易稳定复现，用户最容易验证 |
| 高 | **判据**（怎么判断对错：观察 vs 评论、请求 vs 要求） | 决定 Skill 好不好用 |
| 中 | **原则**（一句话概括的立场） | 提供方向感 |
| 低 | **案例** | 有版权风险，只取骨架 |

**反模式清单的价值常被低估**。一本书里"不要做什么"的部分，往往是 AI 最容易犯错的地方，优先级应高于正面论述。

## 3 · 溯源标注：区分"原著观点"与"我推演的"

这是蒸馏和洗稿的分界线。规则：

- 每个知识点内联标注 `[第X章]`。
- 凡是书里没有、你自己推演的（中文场景化句式、编排方式、补充子项），一律标 `[本仓库扩展]`。
- 引自外部权威材料的标 `[外部依据·来源]`（如 `[外部依据·CNVC课程]`、`[外部依据·WHO]`），并在 `SOURCES.md` 单列一节说明其支撑范围与引用边界。
- **特别注意"半原著"陷阱**：书里给了类名但没给子项（如普世需要 7 大类），补子项时必须标明"非原书列举"。这是最容易无意识编造原著的地方。
- 用一个独立文件（`SOURCES.md`）汇总全部映射与边界声明。

> 判断标准：读者能不能一眼看出"这句话是书里的，还是你加的"。

## 4 · 路由设计：决定什么进上下文、什么时候进

Skill 是**渐进加载**的，结构设计的核心问题是"哪些内容该在什么时候被读进来"。

- **入口（SKILL.md）只放三样**：指针（读哪个文件）、判据（怎么判断对错）、契约（产出什么格式）。定义、例子、清单全部下沉。
- **拆分粒度看触发场景是否重叠**。两个知识点如果几乎不会在同一次对话里被用到，就该拆成两个文件——合在一起等于每次白加载一半。
- **不进上下文的东西放 `assets/`**（模板、图片），用时才读。
- **路由表按"用户动作"和"应用域"两个维度建**，一个横切意图、一个横切场景。

## 5 · 交付契约：让 Skill 产出物，而不只是建议

纯知识型 Skill 的通病是：只输出一段"你应该这样说"的建议，用户还得自己整理。

改进办法是定义**交付契约**：

- **先定档位，再定产物** [本仓库扩展]：快速档（用户只要一句回复 / 正在倾诉）→ 只给口语短句；标准档（"帮我改这句话"）→ 对照卡片 + 短句；学习档（显式要求拆解 / 复盘）→ 完整分析。**不要把所有产物无条件设成默认**——用户只是来要一句话时，先甩一套诊断会让人觉得又被评判了一遍。
- **D1 对照卡片**（如"原文 vs 改写"对照卡片 + 四要素拆解，**仅标准档 / 学习档**）
- **D2 可直接使用的成品**（如 3–5 句可发送短句）
- **D3 落盘**（用户明确要求时才写文件，用 `assets/templates/` 下的模板）

契约写进 SKILL.md，输出格式就稳定了，用户也不用每次重复说明。

## 6 · 用例验证：不跑一遍等于没做

写 30+ 条真实口语用例，每条固定五个字段：

`输入 / 预期路由 / 判据要点 / 翻车点 / 通过`

- **预期路由**检验 description 与路由表有没有写对（召回不到 = 失败）。
- **判据要点**检验 reference 里有没有写出**可判定的**标准（写不出判据 = 那段内容太虚）。
- **翻车点**来自你对这本书最常见的误读——这是最有价值的一列。
- 分组覆盖所有路由分支，另设一组**故障注入**（诱导输出错误结果、模糊表述、越界请求）。

跑完记总评分表：触发准确率、判据命中率。低于阈值就回去改第 4 步。

## 附：安全门禁为什么应放在第 0 步

任何"教人怎么说"的 Skill 都隐含一个风险：用户可能在危机场景下使用它，而**技巧本身会掩盖真正的风险**（例如在家暴关系里要求受害方"先同理对方"）。

处理办法是在工作流最前面加一道**不可跳过的门禁**：

1. 定义明确的触发信号清单（A 类人身安全 / B 类自伤自杀 / C 类灰色信号）。
2. 命中即停用全部常规流程，转向识别—稳定—转介。
3. 准备可直接使用的回应话术与本地求助资源。
4. 写清"明确不做的事"（不做治疗、不为施害者包装话术、不追问细节）。
5. 设误报处理分支，避免过度反应。

门禁的测试用例必须 100% 通过——这是底线，不是加分项。
